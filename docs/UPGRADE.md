# Knowledge Brain 工程审计与升级（2026-10-23）

## 实际架构与取舍

工程是 Python 模块化单体：Click CLI / FastAPI → 采集与处理器 → SQLite + Chroma；Web 前端是一份通过 CDN 加载 React、ECharts、G6 的 HTML。图谱、主题、百科都从 SQLite 读取；外部嵌入与生成服务是可选增强。

保留这一部署方式，升级数据一致性与检索主链路。个人知识库并不存在适用于所有数据规模、成本和隐私要求的“最先进”架构。当前更需要可靠的原文、可检索的分块、跨索引一致性和可验证的检索，而不是增加独立数据库与多代理服务。

| 层 | 本次实现 | 关键约束 |
|---|---|---|
| 采集应用服务 | `kb/services/ingestion.py`，CLI / HTTP 共用 | 去重、元数据、标签、分块在同一 SQLite 写事务中提交 |
| 权威数据 | SQLite 保存文档、正文分块和关联数据；Markdown 保留原始采集产物 | 本地搜索不依赖模型成功 |
| 全文索引 | 文档 FTS5 + 新增正文分块 FTS5 | 创建时回填旧分块，触发器同步增删改；中文子串未命中时回退 LIKE |
| 派生向量 | Chroma 文档与分块集合 | 搜索结果批量回查 SQLite，过滤删除项、更新元数据、执行标签 AND 筛选 |
| 混合检索 | 语义 / 关键词独立召回 → 按文档 ID 的 RRF 融合 | 不混加 BM25、余弦等不同尺度的原始分数 |
| 证据与回答 | 共用上下文打包、引用编号、对话历史和 LLM 配置 | 预算单位为字符；来源列表只包含实际放进上下文的证据 |
| 派生索引删除 | SQLite `vector_deletions` outbox | 向量删除失败保留任务，下次 Web 获取 Chroma 服务时分批重试 |
| 模型增强 | 单工作线程池、复用已保存分块、标题前缀嵌入 | 正常 CLI 退出等待已提交任务；强制终止不保证完成 |

设计依据：

- [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)：全文与向量互补、分块需要上下文。本次采用标题前缀，是轻量上下文增强，不等同于该研究的 LLM 生成逐块上下文，也不继承其质量提升数字。
- [Microsoft GraphRAG 查询说明](https://microsoft.github.io/graphrag/query/overview/)：局部实体问答与全局主题总结是不同查询任务。本工程保留图谱和百科浏览；尚未实现 GraphRAG 社区报告检索或自动路由，不以“六阶段管道”的名称宣称存在未实现阶段。

## 已修复的问题

- 所有笔记 `source=note` 导致不同笔记被当作同一来源去重；笔记现在按内容哈希去重。
- 中文标题在同秒保存可能覆盖同名文件；文件名加入微秒与随机后缀，空转写使用类型名。
- 手写 YAML frontmatter 遇到冒号、换行和列表时无效；使用 YAML 序列化。
- 默认 `title=None` 覆盖笔记、文件和书签的默认标题；空标题回退有效标题。
- CLI / Web 采集逻辑不一致、Web 笔记丢失文件路径和哈希、正文只保留前 30,000 字；统一服务保存完整正文分块。
- 关键词只搜摘要，正文信息无法召回；新增分块 FTS5，返回命中正文与 chunk_id。
- 伪 RRF 先去重后混加原始分数；现按两路各自排名累加倒数，融合前保留交集贡献。
- 标签参数被忽略；全文检索在 SQL 中过滤，向量检索在权威元数据中筛选。
- 超长首篇导致整个上下文为空；按预算截取有效正文，来源与证据保持一致。
- 对话历史重复包含当前问题；先读取历史再记录当前问题。
- 删除后标签计数、文档关系、主题关系和实体提及残留；事务内维护关联及计数，相关百科标记过期。
- Chroma 用文档 ID 删除不同 ID 的分块而失败；按 `knowledge_id` 删除分块。
- SQLite 不支持 `GREATEST`；取消标签改为 `MAX`。
- 分块尾部反复生成短片段；最后一块完成即退出，并校验 overlap 参数。
- 每次采集新增守护线程、CLI 提前退出丢失处理；使用单线程池，并立即保存本地可搜索内容。
- 无嵌入时共享实体关系也被跳过；关系构建不再依赖向量存在。
- 重复实体抽取累加错误计数、重复百科生成新增文章；提及计数从关联计算，百科使用稳定 ID。
- 主题重建先提交清空再写入，失败时丢失原主题；清空与写入同事务提交。
- 更新模型设置后仍复用旧对象；使相关查询依赖失效。单例初始化增加可重入锁。
- 图谱遍历重复展开相同节点/深度，相关文档双向重复；去重并限制 API 遍历范围。
- 百科内容直接插入 HTML；先转义用户/模型文本再生成固定格式标签。
- SQLite 备份直接拷贝运行中的数据库文件；改为在线快照，含已提交 WAL 内容。
- 备份文件名及归档解包缺少边界检查；限制目录并拒绝穿越、符号链接与特殊成员。
- 默认 Web 绑定全部网络接口；默认绑定 127.0.0.1，可显式 `--host` 配置。
- 测试读取真实配置并写个人知识库；隔离 home 解析及 Web 单例。
- 依赖允许 Pydantic 1，但代码使用 v2 API；声明 Pydantic 2 与兼容 FastAPI 下限。

## 验证记录

运行环境：本机 Python 3.14；所有业务数据来自临时目录。没有改写用户真实知识库，没有调用用户付费模型服务。

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m pytest -q
PYTHONDONTWRITEBYTECODE=1 python3 -m benchmarks.retrieval
git diff --check
```

测试：51 项通过，包括真实 Chroma 写入/查询/删除、API 连续采集、CLI 采集搜索、旧库 FTS 回填、事务回滚、向量故障重试、模型故障降级、引用预算与对话历史。

性能样本：2,000 篇合成文档，100 次精确关键词查询全部命中；FTS 中位 0.063 ms，P95 0.083 ms。数据量小、查询精准、缓存温热，仅反映此机器的索引访问开销，不代表中文扫描、复杂查询、真实语义召回或模型端到端性能。

分块回归：200 个字符，块长 100、重叠 20；旧实现生成 23 块，新实现为 3 块。避免重复嵌入调用和尾部索引膨胀。

## 升级与使用

1. 停止旧服务，先保留整个数据目录副本；更新依赖 `pip install -e '.[dev]'`。
2. 启动 `kbrain web`。首次 SQLite 初始化自动创建分块索引、回填已有 chunks，并创建删除队列表，不重建源文档。
3. 新采集内容立即可关键词搜索；旧库只有摘要、缺失 chunks 或已被旧版截断的正文不会凭空恢复。旧版重复笔记文件、重复分块与百科历史不会被自动删除。
4. 模型服务可选；无模型时仍可采集、全文搜索、浏览和查看检索证据。
5. `query.pipeline.rerank_top_k` 现在是融合后的证据数量上限，不代表启用了神经 reranker；`context_budget` 按字符计量。
6. `data_dir` 自定义时，应同时明确配置 `storage.persist_directory` 和 `backup.backup_dir`，避免沿用默认路径。
7. 需要局域网访问时可显式 `kbrain web --host 0.0.0.0`；当前没有用户认证，不应直接暴露到公网。

## 明确的剩余边界与后续演进

- 未使用真实个人语料做人工相关性标注；尚无 Recall@k / MRR / 引用忠实度的质量基线。下阶段应先建立脱敏问答集，再评估重排与图谱路由，不能仅凭架构名称判断收益。
- 当前是文档级融合，每篇选取一个命中片段；未实现多片段融合、神经 reranker、查询改写或完整 GraphRAG。
- 中文 LIKE 回退需要扫描，标签语义搜索是有界过采样后筛选，稀有标签可能不足 top_k；更大语料需专用中文索引与向量预过滤。
- 模型增强尚无持久化作业队列、租约或失败自动恢复；单线程池限制线程数但待处理队列未设置容量。强制退出或模型失败后，本地内容仍可搜索，但增强需要重新执行。
- 删除 outbox 是最终一致性；与正在运行的模型增强并发时可能重新写入孤立向量，查询层仍过滤它们。后续需版本号/墓碑以及增强提交校验。
- 每个 SQLite 快照自身一致，但 Chroma HNSW 文件与其他数据库没有跨存储原子快照。可靠全量备份/恢复仍应在维护窗口进行；恢复 API 仍要求停止并重启服务，不提供在线事务化恢复。
- 模型切换后的向量维度/版本迁移、会话持久化、认证、云备份能力、前端离线资源与完整浏览器交互验收不在本次实现中。README 旧版云备份说明超出当前本地备份路由实际能力。
- Chroma 依赖在 Python 3.14 有一项弃用警告，不影响本次测试；未覆盖所有 Python 3.10+ 环境。
